# The options doc's "launch 6" (docs/spectacle-nca-options.md §6.2; this file is plan-7 because plan-6.txt is the flood
# model's spiral fine-tune): M1 with the rule at the tap (nca/strand/train2.py). Each cell sees only static board facts
# and, on the tapped cell only, the rule's 53-bit code + the tapped chord's two edges (no owner slot: M1 is one player).
# Arms (the owner's pick from the per-cell probe, docs/strand-data.md "v2"), each its own process on the one L4:
#   tap-e    E  local-frame perception (nets.FrameNCA; type one-hot only; equivariant, parity-tested), 96 / 128 / depth 1
#   tap-c    C  per-direction edge classes + anchor + mirror (55 planes), 96 / 128 / depth 1
#   tap-big  C at channels 128, hidden 256, depth 2 (2.6x the parameters; 2.35x C's CPU time per iteration on the Pi)
#   A, D and C-bc are commented out at the end: the probe ranks A <= C at both widths (held-out cell-exact 0.56 / 0.92
#   vs 0.73 / 0.98 at width 128 / 1024) and D far behind (0.12 / 0.59); E-local 0.95 / 0.985.
# Stages per arm (the doc's chain, --init from the previous stage's best.pt; later stages at lr 2e-4, not 5e-4):
#   l2   M1a on level-2 patches                            25 min
#   l3   M1a on levels 2 + 3                              240 min
#   l4   M1a on level 3 + level-4 crops                   150 min
#   m1b  M1b with the tap held (12 planes) on 2 + 3 + 4    60 min
# = 475 min a run + SETUP_MIN 25 = 500 min = ~8.3 VM-hours (MAX_HOURS 12), ~$3.4 at ~$0.41/h (the arms share the GPU,
# so three arms cost the same as four). The VM adds --schedule time (lr steps at 60% / 85% of each stage's minutes).
# BATCH 16 for all three, from memory measured on the Pi's CPU (python -m nca.strand.memprobe: peak RSS of one
# gradient window on level-4 crops, S 42, the largest boards; two window lengths give per step and transient):
#   per backprop step at batch 8: E 19.4 MB (+325 MB transient: its checkpointed 7-tap recompute), C 35.6 MB (+43),
#   big 75.9 MB (+33); autograd's saved tensors are ~70% of that, the rest allocator overhead -- kept, as GPU slack.
#   Window 48 at batch 16: E 2.5 GB, C 3.5 GB, big 7.35 GB; + the pools on the GPU (256 slots x levels 2-4 at m1b,
#   float32: 0.32 / 0.32 / 0.43 GB) + ~0.4 GB of CUDA context each = ~15.6 GB, ~17 GB with 10% allocator slack, of
#   the L4's 24 GB. Batch 32 for E and C with big at 16 would be ~21.6 GB (too close); E / C at 32 with big at 8
#   ~18 GB (~19.8 with slack). Equal batches also keep E vs C vs big a comparison of the nets alone. The quick check's
#   read-out (eval batch 64, no gradient, after the window is freed) peaks at 1.2 GB for E, 0.65 GB for big.
# Throughput (estimated from plan 5's measured GPU rate, not measured on the L4): at batch 16 roughly 0.9 s / iteration
# for E and C and 2.3 s for big while all three share the GPU -- an l3 stage ~15k iterations for E and C, ~6k for big
# (plan 5's m128: ~25k at batch 32). E's per-frame weight selection is untested on a GPU: watch its secPerIter.
# Quick checks: held-out rules only -- the legacy set (train.py's taps on the v1 split's 20 held-out rules: comparable
# with the overnight runs) and the wide set (held-out rules of all 7 subsets), 120 taps per (set, level) at levels 3
# and 4, plus the code-fidelity probe (q.code); score = length-balanced exact (best.pt follows it). Every 1000
# iterations (500 for big; 3000 / 1500 in l2), ~8% of the stage.
# Gates (docs §6.2, readable on the dashboard): at +90 min into l3 an arm with held-out exact >= 0.6 and rising is
# alive; all flat under 0.3 says the per-cell lookup is not learned in the CA (wider nets; the probe learns it); a
# weak q.code.byDist far from the tap says the line does not carry the code (then C-bc, commented out below, is the
# test). Bar: legacy exact >= 0.95 at level 3; long-strand exact against the overnight 0.66 (q.bySet.legacy.byLen.long).
